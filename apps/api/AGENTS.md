# API Agent Guide

This is the read-only Rust and axum service over Postgres and Elasticsearch for the qafiyah.com Arabic poetry catalog. It is versioned under `/v1`, and is contract-first through `utoipa`. If the code no longer matches the committed `generated/openapi/openapi.json`, CI fails (`openapi.rs`).

## Shape

The database and the search index are behind traits, so the dependencies point inward. `routes/` calls the domain. The domain declares what it needs as repository traits. `db/` and `es/` implement them.

- `domain/` is pure, with no I/O.
  - It holds plain types in domain words (`Poem`, `PoemSummary`, `PoetProfile`, `Term`, `PoemHit`, and so on), with no `serde` or `utoipa`. It also holds the filter and facet types.
  - It holds the rules: verse parsing and the assembly of a poem's detail, the visibility and order of facets, the random excerpt, and snippet selection.
  - It holds the traits `PoemRepository`, `PoetRepository`, `TaxonomyRepository`, and `SearchIndex`.
  - A function that applies rules takes its repository as an argument (`poems::get(state.poems.as_ref(), slug)`). A plain read calls the repository directly.
  - The domain knows nothing about HTTP. It returns its own errors: `PoemError`, and `StoreError`, the failure that every repository and the search index return. `error.rs` maps them to problem responses.
  - Request parsing (the query parameters, and the `?option` of the random poem) and the 404 resource of each taxonomy kind are in `routes/`.
- `contract/` holds the public JSON and OpenAPI types (`PoemDetail`, `PoemListItem`, `PoetStats`, `CountedStats`, `PoemResult`, and the `*Ref` types). Each is built from its domain type with `From`.
  - Their fields carry `///` descriptions. This is the one kind of doc comment that the conventions allow, because utoipa publishes them as the OpenAPI field descriptions.
  - Handlers convert at the edge (`PoemDetail::from(poem)`). So a new name for a domain field never changes the contract, and the committed `generated/openapi/openapi.json` stays the check of that.
  - The account routes keep their request and response bodies (`IdentityBody`, `ProfileView`, `KeySummary`) in `routes/account.rs`, in the same way.
- `params.rs` and `extract.rs` are the request side.
  - `SafeQuery<T>` (`serde_html_form` and `serde_path_to_error`) decodes every query into one `#[derive(Deserialize, utoipa::IntoParams)]` struct for each endpoint. That struct also generates the endpoint's spec parameters.
  - Each value type in `params.rs` (`FourLetterSlug`, `TransliteratedSlug`, `Page<MAX>`, `SearchText`, `PoetSlugs`, `TermSlugs`) pairs its check with its schema.
  - Unknown parameters are refused (`deny_unknown_fields`, and `NoParams` on operations that take none). The `detail` of every 400 names the parameter.
  - Derive `utoipa::IntoParams` and implement `utoipa::PartialSchema` by their full path. Do not import the traits. utoipa's macros write those paths with the span of the field, and `unused_qualifications` refuses them when the trait is imported.
- `accounts/` does the same for the separate `qafiyah_accounts` database.
  - It holds key generation and hashing, session ids and their TTL, email normalization, the key cache, and the usage recorder.
  - It holds the traits `UserRepository`, `SessionRepository`, `KeyRepository`, and `UsageRepository`.
  - Its schema is in `apps/api/migrations/`, the only migrations in the repo. There is one directory for each migration, with an `up.sql`, and Diesel applies them at startup. The corpus database has no migrations; the `data/db/` dumps manage it.
- `db/` holds the Postgres adapters. It is the only code that uses Diesel.
  - `mod.rs` holds the deadpool pool (`pool`, `corpus_setup`, `accounts_setup`).
  - It also holds the typed schemas. `db::corpus` is re-exported from `crates/corpus`. `db::accounts_schema` is generated by `bun run db:schema` from the dev databases, and checked with `bun run db:schema:check`.
  - It also holds the SQL functions that the queries call, `migrate` (which applies `migrations/` at startup), and `Uncached`. `Uncached` sends one query unnamed, so Postgres plans it for its values (see `docs/exceptions.md`).
  - There is one file for each repository (`PgPoems`, `PgPoets`, `PgTaxonomy`, `PgUsers`, `PgSessions`, `PgKeys`, `PgUsage`).
  - Adapters return `domain::StoreError`, never `AppError`. "Not found" is `None`.
  - A pool that times out or cannot reach Postgres gives `StoreError::Unavailable` (503 with `Retry-After`). Any other failure is `Database` (500).
- `es/` is the Elasticsearch adapter.
  - `es/query.rs` holds the query bodies, with their relevance tiers.
  - `es/client.rs` is the client. It reports these as `StoreError::Unavailable`: a search that times out, a search that cannot connect, and a 429, 503, or 504 from Elasticsearch. The message holds the HTTP client's whole cause chain. So a failed lookup, a refused connection, and a timeout look different in the log.
  - `es/search.rs` deserializes the responses into typed hits, and implements `SearchIndex` for `Es`. A missing field fails the search, so it never shows empty text.
- `state.rs`: `AppState` holds every repository as `Arc<dyn Trait>`. `AppState::new` connects the Postgres and Elasticsearch adapters. A test can replace any field with a fake.
- `routes/` has one file for each resource, connected to the OpenAPI contract in `lib.rs::app`.
- `metrics.rs`: the outermost layer records every request into the native histogram `http_server_request_duration_seconds`, by method, status, and the matched route template (or `unmatched`).
  - `es::client::Es::search` records every Elasticsearch search into `db_client_operation_duration_seconds`, by alias.
  - `Metrics` is in `AppState`, so each test reads its own.
  - When `METRICS_PORT` is set, `main.rs` serves `metrics::router` on that port, in the Prometheus protobuf format. Only compose sets it, to 9464, which is not published. The public router never serves `/metrics`.
  - What reads the metrics is in `apps/observability/AGENTS.md`.
- `log.rs` is the logging, through `tracing`.
  - `subscriber` builds the one JSON subscriber. `main.rs` writes it to stdout, and the tests to a buffer.
  - `trace` is `tower-http`'s `TraceLayer`, with a `request` span for each request. The span has the method, the route, the path, the request id, and every field that a handler records with `tracing::Span::current().record`. All fields are declared at the start, because tracing drops an undeclared field without a message.
  - A closing `request` event gets its level from the production rule: `error` for 5xx, `warn` over 2 seconds, and `debug` for the rest.
  - `record_results` records a result count, and logs `info` "found nothing" at zero.
  - `tower-http`'s request-id layers set and return `x-request-id`.
- The layers:
  - `cors`, the request-id and trace layers, and `error` wrap every route. `rate_limit` wraps the whole `/v1` nest.
  - Inside `error`, a 6-second deadline (`REQUEST_DEADLINE_SECONDS`, tower's `TimeoutLayer` behind axum's `HandleErrorLayer`) answers 503 to a request that runs longer. This is above the 5-second query and search timeouts, and below the website's 8-second proxy timeout and 10-second render timeout.
  - `cache` also wraps the routes of the OpenAPI router, and only those.
  - `routes::poems::random` and the `go` redirect routes are merged outside the cache layer on purpose (see `lib.rs::app`). The random poem is still in the OpenAPI document, listed in the `paths` of `ApiDoc`.
- `generated/`: nothing here is written by hand (see "Generated files" in `docs/code-conventions.md`).
  - `openapi/openapi.json` is the output of `document()`. The drift test in `openapi.rs` checks against it. To generate it again, run `bun run openapi:snapshot`.
  - `es/query.vectors.json` is the output of the Elasticsearch query builder. The drift test in `src/bin/es-query-dump.rs` checks against it. To generate it again, run `bun run es:query:snapshot`.
  - Only `#[cfg(test)]` code includes these two files, with `include_str!` at compile time. So if they move or are missing, only `cargo test` is affected, never a release build.
  - `diesel/accounts.gen.rs` is the accounts Diesel schema that `db/mod.rs` compiles in. The corpus schema is in `crates/corpus`. After a dump that changes the corpus schema, or after a new accounts migration, generate both again with `bun run db:schema`.

## Tests

There are three tiers, cheapest first.

**Inline tests.** Unit tests and seeded property tests are next to the code that they cover.

**`http_tests/`** drives the assembled `app()` in the process, with `tower::ServiceExt::oneshot`. It uses `test_support.rs` for these things:

- lazy database pools that fail on first use. `http_tests/catalog.rs` uses in-memory repository fakes instead, which test a handler's behavior without a database.
- a `FakeEs` listener that records every body it receives
- request helpers, and a deterministic `Rng`

So a 503 from one of those routes proves that the request tried to use the database, and a 400 proves that it did not.

**`tests/db.rs`** runs every contract operation and the accounts flows against the dump that is loaded.

- It returns early unless all three `QAFIYAH_TEST_*` variables are set. So plain `cargo test` needs no infrastructure. `bun run rust:test:db` sets them from the dev stack.
- The search guards in `tests/db/search.rs` also need `QAFIYAH_TEST_ELASTICSEARCH_ADMIN_URL`, which `bun run rust:test:db` sets. They build a throwaway index from `schema.json` with prepared poems or poets, and delete it after.
- Every search rule is tested there by what a search returns: recall, ranking and its tie-breaks, the classical-era and typed-hamza boosts, alternate readings, browse order, facets, and poet order.
- `es/query.rs` keeps only two checks: that every field a query names exists in the mappings, and the paging arithmetic. `generated/es/query.vectors.json` catches any change to the request bodies.
- Each accounts test runs inside `Harness::isolated`, which deletes its user even when the test panics.

Request examples are only in the `example` of each parameter, never in description text. `bun run api:conformance`, which the origin smoke run calls, sends them through Schemathesis. It fails unless every operation answers 2xx. So an example must exist in the 100-poem sample, and in the full dump.

Tests check what a caller sees (responses, rows, pages), not how the code produces it. There is one exception: the two SQL-shape tests in `db/poems.rs`. They require `= $n` for one id and `= ANY` for several, because that shape is the planner requirement in `docs/exceptions.md`.

## Everything else

Key comparison, CORS, error shapes (RFC 9457 problem+json), caching (ETag and Cache-Control), and OpenAPI generation beyond the contract-drift check are ordinary axum and utoipa plumbing. Each has one file, and nothing in them is unexpected.
