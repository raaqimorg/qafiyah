# API Agent Guide

Read-only Rust/axum service over Postgres + Elasticsearch for the qafiyah.com Arabic poetry catalog. Versioned under `/v1`, contract-first via `utoipa` (the committed `generated/openapi/openapi.json` fails CI if the code drifts from it, `openapi.rs`).

## Shape

The database and the search index sit behind traits, so dependencies point inward: `routes/` call the domain, the domain declares what it needs as repository traits, and `db/` and `es/` implement them.

- `domain/`: pure, no I/O. Plain types in domain vocabulary (`Poem`, `PoemSummary`, `PoetProfile`, `Term`, `PoemHit`, and so on, with no `serde` or `utoipa`), the filter and facet types, the rules (verse parsing and poem detail assembly, facet visibility and order, the random excerpt, snippet selection), and the traits `PoemRepository`, `PoetRepository`, `TaxonomyRepository`, and `SearchIndex`. A function that applies rules takes its repository as an argument (`poems::get(state.poems.as_ref(), slug)`); a plain read calls the repository directly. The domain knows nothing of HTTP: it returns its own errors (`PoemError`, and `StoreError`, the failure every repository and the search index return), `error.rs` maps them to problem responses, and request parsing (query parameters, the `?option` of the random poem) and the 404 resource of each taxonomy kind live in `routes/`.
- `contract/`: the public JSON and OpenAPI types (`PoemDetail`, `PoemListItem`, `PoetStats`, `CountedStats`, `PoemResult`, and the `*Ref` types), each built from its domain type with `From`. Handlers convert at the edge (`PoemDetail::from(poem)`), so renaming a domain field never changes the contract, and the committed `generated/openapi/openapi.json` stays the check that it did not. The account routes keep their request and response bodies (`IdentityBody`, `ProfileView`, `KeySummary`) in `routes/account.rs` the same way.
- `accounts/`: the same for the separate `qafiyah_accounts` database: key generation and hashing, session ids and their TTL, email normalization, the key cache, the usage recorder, and the traits `UserRepository`, `SessionRepository`, `KeyRepository`, and `UsageRepository`. Its schema lives in `apps/api/migrations/`, the repo's only migrations (one directory per migration with an `up.sql`, applied by Diesel at startup); the corpus database is still managed by `data/db/` dumps and has no migrations.
- `db/`: the Postgres adapters, the only code that uses Diesel. `mod.rs` holds the deadpool pool (`pool`, `corpus_setup`, `accounts_setup`), the typed schemas `db::corpus` (re-exported from `crates/corpus`) and `db::accounts_schema` (generated by `bun run db:schema` from the dev databases, checked with `bun run db:schema:check`), the SQL functions the queries call, `migrate`, which applies `migrations/` at startup, and `Uncached`, which sends one query unnamed so Postgres plans it for its values (see `docs/exceptions.md`). One file per repository (`PgPoems`, `PgPoets`, `PgTaxonomy`, `PgUsers`, `PgSessions`, `PgKeys`, `PgUsage`). Adapters return `domain::StoreError`, never `AppError`, and "not found" is `None`. A pool that times out or cannot reach Postgres is `StoreError::Unavailable` (503 with `Retry-After`); any other failure is `Database` (500).
- `es/`: the Elasticsearch adapter: the query bodies with their relevance-ranking tiers (`es/query.rs`), the client (`es/client.rs`), which reports a search that times out, cannot connect, or gets a 429, 503, or 504 from Elasticsearch as `StoreError::Unavailable`, and `es/search.rs`, which deserializes the responses into typed hits (a missing field fails the search instead of showing empty text) and implements `SearchIndex` for `Es`.
- `state.rs`: `AppState` holds every repository as `Arc<dyn Trait>`. `AppState::new` wires the Postgres and Elasticsearch adapters; a test can replace any field with a fake.
- `routes/`: one file per resource, wired into the OpenAPI contract in `lib.rs::app`.
- `cors`, `log`, `error` wrap every route; `rate_limit` wraps the whole `/v1` nest. Inside `error`, a 6 s deadline (`REQUEST_DEADLINE_SECONDS`, tower's `TimeoutLayer` behind axum's `HandleErrorLayer`) answers 503 to a request that runs past it: above the 5 s query and search timeouts, below the website's 8 s proxy and 10 s render timeouts. `cache` additionally wraps only the OpenAPI-contract routes (`routes::poems::random` and the `go` redirect routes are merged in outside the cache layer on purpose, see `lib.rs::app`).
- `generated/`: nothing here is hand-authored (see `docs/code-conventions.md`'s "Generated files" rule): `openapi/openapi.json` is the `document()` output checked against by `openapi.rs`'s drift test (regenerate with `bun run openapi:snapshot`); `es/query.vectors.json` is the ES query-builder output checked by `es-query-dump.rs`'s drift test (regenerate with `bun run es:query:snapshot`). Both are compile-time `include_str!`'d only from `#[cfg(test)]` code, so moving or missing them never affects a release build, only `cargo test`. `diesel/accounts.gen.rs` is the accounts Diesel schema `db.rs` compiles in (the corpus one lives in `crates/corpus`); regenerate both with `bun run db:schema` after a dump that changes the corpus schema or a new accounts migration.

## Tests

Three tiers, cheapest first. Unit and seeded property tests sit inline next to the code they cover. `http_tests/` drives the assembled `app()` in process with `tower::ServiceExt::oneshot`, using `test_support.rs` for lazy database pools that fail on first use (or, in `http_tests/catalog.rs`, in-memory repository fakes that test a handler's behavior without a database), a `FakeEs` listener that records every body it receives, request helpers, and a deterministic `Rng`; a 503 from one of those routes therefore proves the request reached for the database, and a 400 proves it did not. `tests/db.rs` runs every contract operation and the accounts flows against whatever dump is loaded, and returns early unless all three `QAFIYAH_TEST_*` variables are set, so plain `cargo test` needs no infrastructure; `bun run rust:test:db` sets them from the dev stack. The search guards in `tests/db/search.rs` also need `QAFIYAH_TEST_ELASTICSEARCH_ADMIN_URL` (set by `bun run rust:test:db`), because they build a throwaway index from `schema.json` with crafted poems or poets and delete it afterwards. Every search rule (recall, ranking and its tie-breaks, the classical-era and typed-hamza boosts, alternate readings, browse order, facets, poet ordering) is tested there by what a search returns; `es/query.rs` keeps only the check that every field a query names exists in the mappings and the paging arithmetic, and `generated/es/query.vectors.json` catches any change to the request bodies. Each accounts test runs inside `Harness::isolated`, which deletes its user even when the test panics. Tests check what a caller sees (responses, rows, pages) rather than how the code produces it; the one exception is the pair of SQL-shape tests in `db/poems.rs` that pin `= $n` for one id and `= ANY` for several, because that shape is the planner requirement in `docs/exceptions.md`.

## Everything else

Key comparison, CORS, error shapes (RFC 9457 problem+json), caching (ETag/Cache-Control), OpenAPI generation beyond the contract-drift check: ordinary axum/utoipa plumbing, one file each, no surprises.
